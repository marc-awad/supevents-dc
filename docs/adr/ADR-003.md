# ADR-003 — L'idempotence des webhooks Stripe est garantie par déduplication via Redis sur l'identifiant d'événement Stripe

**Statut** : Accepté  
**Date** : 07/05/2026  
**Auteurs** : Killian DOIZELET

---

## Contexte

Stripe garantit une livraison `at-least-once` de ses webhooks : un même événement (ex : `payment_intent.succeeded`) peut être envoyé plusieurs fois en cas de timeout de notre endpoint, de redémarrage de notre serveur, ou d'incident réseau. Stripe recommande explicitement d'implémenter l'idempotence côté receveur.

Sans idempotence, recevoir deux fois le même webhook `payment_intent.succeeded` déclencherait deux confirmations de ticket, deux publications d'événement RabbitMQ, et potentiellement deux emails de confirmation — dégradant l'expérience utilisateur et corrompant l'état du système.

La question est : quel mécanisme retenir pour détecter et ignorer les replays de webhooks ?

---

## Décision

Nous retenons la **déduplication par identifiant d'événement Stripe** stocké dans Redis. À la réception de chaque webhook :
1. On extrait `event.id` (ex : `evt_1234abcd`) du payload Stripe.
2. On interroge Redis avec la clé `webhook:{event.id}`.
3. Si la clé existe → le webhook a déjà été traité → on retourne 200 OK immédiatement.
4. Si la clé n'existe pas → on la crée avec valeur `"processing"`, on traite le webhook, puis on la met à jour avec `"processed"`. TTL : 24 heures.

---

## Alternatives envisagées

### Alternative 1 — Déduplication en base PostgreSQL (table `webhook_events`)

Créer une table `webhook_events(stripe_event_id UNIQUE, processed_at)`. À chaque réception, faire un `INSERT OR IGNORE`. Si l'insertion échoue (doublon), le webhook est un replay.

*Raison de l'écart :* La déduplication PostgreSQL est plus persistante (les données survivent au-delà de 24h) et ne dépend pas de Redis. Cependant, elle ajoute une écriture en base sur le chemin critique de chaque webhook, augmentant la latence. Elle nécessite aussi une politique de purge pour éviter une croissance indéfinie de la table. Redis avec TTL est plus simple et suffisant pour le besoin : 24h de fenêtre de déduplication couvre largement les cas de retry Stripe (Stripe réessaie sur une période de 3 jours maximum, mais les replays tardifs — > 24h — sont traités comme de nouveaux événements et nécessitent une investigation manuelle de toute façon).

### Alternative 2 — Idempotence applicative par statut du paiement

Ne pas maintenir de registre de webhooks reçus, mais rendre le traitement idempotent en vérifiant le statut courant du paiement : si `payment.status == "captured"`, ignorer le webhook `payment_intent.succeeded`.

*Raison de l'écart :* Cette approche est fragile en cas de race condition : si deux instances du backend reçoivent le webhook simultanément, les deux lisent `status = "pending"`, les deux traitent, et on retrouve le problème de double traitement. Elle nécessite un verrou supplémentaire sur la table Payment, ce qui revient à reconstruire un mécanisme de déduplication plus complexe que Redis. De plus, elle ne couvre pas les replays de webhooks d'autres types (ex : `payment_intent.payment_failed` reçu deux fois).

### Alternative 3 — Vérification via l'API Stripe (re-fetch de l'événement)

À la réception de chaque webhook, faire un GET sur l'API Stripe pour récupérer l'événement complet et vérifier son statut réel, plutôt que de faire confiance au payload reçu.

*Raison de l'écart :* Ajoute un appel Stripe sur le chemin critique (latence + dépendance externe au moment le plus critique). Ne résout pas le problème des replays (deux webhooks identiques feraient deux GET identiques). Utilisable comme vérification de sécurité supplémentaire (non comme mécanisme d'idempotence principal).

---

## Conséquences

### Positives

- Garantie forte : aucun webhook ne peut être traité deux fois dans une fenêtre de 24h.
- Implémentation simple et rapide (2 opérations Redis GET/SET).
- Redis est déjà dans le stack (pas de nouvelle infrastructure).
- TTL automatique : pas de purge manuelle à gérer.

### Négatives

- Si Redis est indisponible au moment de la réception d'un webhook, la vérification d'idempotence est impossible. Pour ce cas, le choix retenu est de **rejeter le webhook** (retourner 503 à Stripe) plutôt que de risquer un double traitement. Stripe retentera automatiquement.
- Fenêtre de déduplication de 24h : un replay après 24h serait traité comme un nouveau webhook. Ce cas est théoriquement possible mais non documenté dans les pratiques Stripe ; si cela se produit, l'état incohérent devra être corrigé manuellement.
- La clé Redis `webhook:{event.id}` n'est pas persistée sur disque par défaut. Si Redis redémarre sans persistance activée, les clés sont perdues. **Mitigation :** configurer Redis avec `appendonly yes` (AOF persistence) en production.

### Dette acceptée

La configuration Redis AOF est à valider en TP 1.8 lors de la configuration de l'environnement de production. Sans AOF, un redémarrage de Redis pendant la fenêtre de 24h pourrait permettre un double traitement. Cette configuration est documentée comme un prérequis de déploiement en production dans §6.3.
