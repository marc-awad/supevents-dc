# ADR-002 — Le verrou pessimiste (SELECT FOR UPDATE) est retenu pour la gestion de la concurrence sur la jauge des places

**Statut** : Accepté  
**Date** : 07/05/2026  
**Auteurs** : Marc AWAD, Killian DOIZELET

---

## Contexte

SupEvents doit gérer des inscriptions concurrentes sur des événements à jauge limitée. Lors de l'ouverture des inscriptions pour un événement populaire, plusieurs centaines d'étudiants peuvent tenter de s'inscrire simultanément. La contrainte métier est absolue : il ne doit jamais y avoir plus d'inscrits que la capacité de l'événement, même en cas de forte concurrence.

Le problème est une race condition classique : deux transactions lisent simultanément `remaining_spots = 1`, toutes deux considèrent qu'il reste une place, et toutes deux insèrent un ticket — résultant en `remaining_spots = -1` et deux étudiants inscrits pour une seule place.

Deux familles d'approches existent pour résoudre ce problème : les verrous pessimistes (bloquer l'accès concurrent dès la lecture) et les verrous optimistes (détecter les conflits à l'écriture et réessayer).

---

## Décision

Nous retenons le **verrou pessimiste** avec `SELECT ... FOR UPDATE` sur la ligne `Event` correspondante lors de toute transaction d'inscription. L'opération atomique est : `SELECT FOR UPDATE` → vérification de `remaining_spots` → `INSERT ticket` → `UPDATE remaining_spots - 1` → `COMMIT`.

---

## Alternatives envisagées

### Alternative 1 — Verrou optimiste (Optimistic Locking avec numéro de version)

Chaque ligne `Event` porte un champ `version INT`. Au moment de l'UPDATE, on vérifie que `version = version_lue`. Si une autre transaction a modifié entre-temps, l'UPDATE retourne 0 lignes modifiées → la transaction est réessayée (retry avec backoff exponentiel, max 3 tentatives).

*Raison de l'écart :* Le verrou optimiste est plus performant dans un contexte à **faible contention** (peu de conflits). Mais pour SupEvents, lors de l'ouverture des inscriptions (cas du "thundering herd"), la contention est **élevée et prévisible**. Dans ce cas, le verrou optimiste génère de nombreux retries coûteux, potentiellement des timeouts côté client, et une expérience dégradée. De plus, la logique de retry doit être implémentée et testée côté applicatif, ajoutant de la complexité.

### Alternative 2 — File de réservation (Queue-based reservation)

Les demandes d'inscription sont empilées dans une file RabbitMQ. Un consumer unique traite les demandes séquentiellement, éliminant toute concurrence. Les étudiants reçoivent un accusé de réception immédiat et une confirmation asynchrone.

*Raison de l'écart :* Cette approche élimine la contention mais introduit une latence de confirmation perçue par l'utilisateur (il ne sait pas immédiatement s'il est inscrit). Elle complexifie le frontend (UI optimiste avec statut "en cours de traitement") et ajoute un composant d'infrastructure critique. Le gain est réel à très fort volume (> 10 000 inscriptions/seconde), mais disproportionné pour SupEvents.

### Alternative 3 — Compteur atomique Redis (DECR)

Utiliser `REDIS DECR event:{id}:remaining_spots` pour décrémenter atomiquement et rejeter si le compteur passe en négatif. La base de données est synchronisée en arrière-plan.

*Raison de l'écart :* Cette approche décorrèle la source de vérité (Redis) de la persistance (PostgreSQL). En cas de crash Redis entre le DECR et la synchronisation PostgreSQL, des places peuvent être considérées comme prises sans ticket créé. La réconciliation est complexe et risquée. La cohérence finale n'est pas suffisante pour une contrainte métier aussi forte que "zéro surréservation".

---

## Conséquences

### Positives

- Garantie ACID absolue : la surréservation est impossible. La correction est assurée par le moteur PostgreSQL, pas par la logique applicative.
- Implémentation simple et testable : une seule transaction, pas de retry applicatif.
- Compatible avec les contraintes PCI-DSS (atomicité de l'opération réservation + paiement).

### Négatives

- Le verrou `FOR UPDATE` sérialise les inscriptions concurrentes sur un même événement : le débit maximal d'inscription pour un événement est limité par le temps de traitement d'une transaction (~50-100 ms), soit environ 10-20 inscriptions/seconde par événement.
- En cas de forte concurrence, les transactions en attente du verrou tiennent une connexion PostgreSQL ouverte, ce qui peut saturer le pool de connexions.
- Solution de mitigation : PgBouncer (connection pooling) avec pool size ajusté, et timeout de transaction à 5 secondes pour éviter les blocages indéfinis.

### Dette acceptée

Le débit maximal de ~20 inscriptions/seconde par événement est suffisant pour la v1 (estimé sur la population étudiante cible). Si SupEvents évolue vers des événements avec milliers d'inscriptions/minute (ex : concert national), il faudra revisiter cette décision vers la file de réservation (Alternative 2), ce qui constitue une refactoring majeur. Cette évolution est documentée dans le backlog technique (§12).
