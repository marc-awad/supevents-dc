# §6.2 — Vue des processus

*Dernière mise à jour : 13/05/2026*

Cette section documente les flux dynamiques du système SupEvents via des diagrammes de séquence UML. Elle couvre le parcours nominal d'inscription à un événement payant et le cas d'échec de paiement. Ces diagrammes sont destinés aux développeurs qui implémentent les modules concernés et aux testeurs qui définissent les scénarios de test d'intégration.

---

## §6.2.1 — Séquence : Inscription à un événement (parcours nominal)

Ce diagramme couvre le flux complet depuis le clic "S'inscrire" jusqu'à la réception du ticket par email. Il met en évidence l'enchaînement synchrone du parcours de paiement (étapes 1 à 7) et le découplage asynchrone de la notification (étapes 8 à 9). Le point d'architecture clé est l'utilisation de RabbitMQ comme tampon entre la confirmation du ticket et l'envoi email — si SendGrid est indisponible, l'inscription reste confirmée et la notification sera livrée dès la reprise.

```mermaid
sequenceDiagram
    actor Étudiant
    participant Frontend
    participant Gateway as API Gateway
    participant Auth as AuthModule
    participant Event as EventModule
    participant Ticket as TicketModule
    participant Payment as PaymentModule
    participant PG as PostgreSQL
    participant Stripe
    participant RabbitMQ
    participant Notif as NotificationModule

    Étudiant->>Frontend: Clic "S'inscrire" sur l'événement
    Frontend->>Gateway: POST /api/v1/tickets {event_id, user_id}
    Gateway->>Auth: Valider JWT Bearer token
    Auth->>Auth: Vérifier signature JWT, expiration, rôle
    Auth-->>Gateway: Token valide, user_id extrait

    Gateway->>Event: GET disponibilité places (event_id)
    Event->>PG: SELECT places_restantes WHERE id = event_id FOR SHARE
    PG-->>Event: 12 places restantes
    Event-->>Gateway: Disponible ✓

    opt Liste d'attente si jauge = 0
        Gateway-->>Frontend: 200 {status: "waitlisted", position: N}
        Frontend-->>Étudiant: Ajouté à la liste d'attente
    end

    Gateway->>Ticket: Créer réservation pending
    Ticket->>PG: BEGIN TRANSACTION
    Ticket->>PG: SELECT places_restantes FOR UPDATE
    Ticket->>PG: INSERT ticket {status: "pending"}
    Ticket->>PG: UPDATE event SET places_restantes = places_restantes - 1
    Ticket->>PG: COMMIT
    PG-->>Ticket: ticket_id = "abc-123"
    Ticket-->>Gateway: {ticket_id, status: "pending"}

    Gateway->>Payment: Initier paiement
    Payment->>Stripe: POST /payment_intents {amount, currency: "eur", metadata: {ticket_id}}
    Stripe-->>Payment: {payment_intent_id, client_secret}
    Payment->>PG: INSERT payment {status: "pending", intent_id}
    Payment-->>Gateway: {client_secret}
    Gateway-->>Frontend: {client_secret, ticket_id}
    Frontend-->>Étudiant: Affiche formulaire de paiement Stripe

    Étudiant->>Stripe: Saisit données carte (Stripe.js côté client)
    Stripe-->>Étudiant: Paiement en cours...

    alt Paiement réussi
        Stripe->>Gateway: Webhook POST /api/v1/payments/webhook\n{type: "payment_intent.succeeded"}
        Gateway->>Payment: Vérifier signature HMAC Stripe-Signature
        Payment->>Payment: stripe.webhooks.constructEvent(payload, sig, secret)
        Payment->>PG: UPDATE payment SET status = "captured"
        Payment->>Ticket: Confirmer ticket (ticket_id)
        Ticket->>PG: UPDATE ticket SET status = "confirmed"
        Ticket->>Ticket: Générer QR code HMAC(ticket_id, secret)
        Ticket->>PG: UPDATE ticket SET qr_code = "..."
        Ticket-->>Payment: ticket confirmé
        Payment->>RabbitMQ: publish "ticket.confirmed" {ticket_id, user_id, event_id, qr_code}
        Payment-->>Gateway: 200 OK
        Gateway-->>Stripe: 200 OK (accusé réception webhook)
        RabbitMQ-->>Notif: consume "ticket.confirmed"
        Notif->>Notif: Générer email HTML depuis template
        Notif->>PG: INSERT notification {status: "sent"}
        Notif-->>Étudiant: Email "Votre ticket est confirmé 🎟️"
    else Paiement échoué
        Note over Stripe,Payment: Voir §6.2.2 — Échec de paiement
    end
```

## §6.2.2 — Séquence : Échec de paiement

Ce diagramme traite les deux cas d'échec distincts lors de la phase de paiement. Le cas de refus explicite (réponse immédiate de Stripe) est le plus simple : la réservation est libérée immédiatement. Le timeout Stripe est plus délicat : en l'absence de webhook, un job de réconciliation périodique doit détecter et libérer les réservations bloquées en statut `pending` depuis plus de 15 minutes.

```mermaid
sequenceDiagram
    actor Étudiant
    participant Frontend
    participant Gateway as API Gateway
    participant Payment as PaymentModule
    participant Ticket as TicketModule
    participant PG as PostgreSQL
    participant Stripe
    participant RabbitMQ
    participant Notif as NotificationModule
    participant Logger

    Note over Étudiant, PG: État initial : ticket en statut "pending", PaymentIntent créé

    Stripe->>Gateway: Webhook POST /api/v1/payments/webhook
    Gateway->>Payment: Vérifier signature HMAC Stripe-Signature
    Payment->>Payment: stripe.webhooks.constructEvent(payload, sig, secret)

    alt Refus explicite (réponse Stripe immédiate)
        Payment->>PG: UPDATE payment SET status = "failed", failure_reason = "card_declined"
        Payment->>Ticket: Libérer réservation (ticket_id)
        Ticket->>PG: UPDATE ticket SET status = "cancelled"
        Ticket->>PG: UPDATE event SET places_restantes = places_restantes + 1
        Ticket-->>Payment: Réservation libérée
        Payment->>Logger: LOG ERROR {ticket_id, reason: "card_declined", timestamp}
        Payment->>RabbitMQ: publish "payment.failed" {ticket_id, user_id, reason: "card_declined"}
        RabbitMQ-->>Notif: consume "payment.failed"
        Notif-->>Étudiant: Email "Paiement refusé — nouvelle tentative possible"
        Payment-->>Gateway: 200 OK
        Gateway-->>Frontend: 200 OK
        Frontend-->>Étudiant: "Paiement refusé. Veuillez réessayer."
    else Timeout Stripe (absence de webhook après délai)
        Note over Payment: Job de réconciliation (cron toutes les 5 min)
        Payment->>PG: SELECT tickets WHERE status = "pending"\nAND created_at < NOW() - INTERVAL '15 minutes'
        PG-->>Payment: [ticket_id: "abc-123", ...]
        Payment->>Stripe: GET /payment_intents/{intent_id}
        Stripe-->>Payment: {status: "canceled" ou "requires_action"}
        Payment->>PG: UPDATE payment SET status = "timeout"
        Payment->>Ticket: Libérer réservation (ticket_id)
        Ticket->>PG: UPDATE ticket SET status = "cancelled"
        Ticket->>PG: UPDATE event SET places_restantes = places_restantes + 1
        Payment->>Logger: LOG WARN {ticket_id, reason: "payment_timeout", intent_id}
        Payment->>RabbitMQ: publish "payment.failed" {ticket_id, user_id, reason: "timeout"}
        RabbitMQ-->>Notif: consume "payment.failed"
        Notif-->>Étudiant: Email "Votre réservation a expiré — places disponibles sous réserve"
    end
```
